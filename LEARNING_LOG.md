# What I Learned Today

A running log of what I build and learn while working on FreelanceOS, a full-stack SaaS platform for freelancers (React/TypeScript + FastAPI/PostgreSQL, with AI features planned). Building this project end-to-end, hand-in-hand, as part of prep for AI/full-stack engineering roles.

---

## 2026-08-02

Started Phase 1 today — authentication. First real coding day since the project skeleton, so a lot of the day was fixing my own typos and reading stack traces.

Built `backend/database.py` first: the SQLAlchemy `engine` (connection pool to Postgres, built once from `DATABASE_URL`), a `SessionLocal` factory for per-request DB sessions, a `Base` class for models to inherit from, and a `get_db()` generator that FastAPI uses as a dependency (yields a session, closes it after, even on errors). Along the way I typo'd `declarative_base` as `Declarative_base` and then tried to subclass it like it was a class instead of calling it like the function it actually is — two different errors from the same root confusion, fixed once I slowed down and read what Python was actually saying.

Next was the `User` model — id, email (unique + indexed since it's the login key), hashed_password, is_active, created_at (timezone-aware, defaults to `now()` on the DB side). Ran it against real Postgres instead of assuming it worked, and hit an actual bug: `.env` had the Postgres username wrong (`freelanceos` vs `freelancer`, one letter off from what docker-compose actually created), which Postgres reported as "password authentication failed" — misleading, since the real problem was the username, not the password. Fixed the `.env` value and it connected fine.

Added `full_name` to the model afterward, which meant the live table was now out of sync with the Python model — `create_all()` only creates missing tables, it doesn't alter existing ones. Used that as a reason to set up Alembic properly instead of dropping and recreating the table. Ran `alembic init`, wired `env.py` to load the DB URL from `.env` and to import the `User` model (learned that a model has to be imported somewhere or `Base.metadata` has no idea it exists), then ran `alembic revision --autogenerate` and it correctly detected the one column that had changed. Applied it with `alembic upgrade head` and confirmed with `\d users` in psql that the column was actually there. Also now know that adding a `NOT NULL` column with no default breaks if the table already has rows — didn't hit it today since the table was empty, but worth remembering.

Then password hashing — `hash_password()` / `verify_password()` wrapping passlib's `CryptContext` with bcrypt. Hit a genuinely confusing dependency issue here: passlib 1.7.4 doesn't know how to talk to bcrypt 5.0 (some internal version-detection thing broke), and the error it threw ("password cannot be longer than 72 bytes") had nothing to do with the actual problem. Pinned `bcrypt==4.0.1` in requirements.txt and it started working. Good reminder that a weird error doesn't always mean the bug is in your own code — sometimes it's two libraries disagreeing with each other.

Finished with Pydantic schemas — `UserCreate`, `UserOut`, `UserLogin`. The useful thing here was understanding why `UserOut` is a separate shape from the DB model at all: it should never be able to leak `hashed_password`, and because Pydantic only reads the fields you explicitly declare, it can't — even if you hand it an object that has a password field sitting right on it. Tested that directly instead of just assuming it. Also needed `class Config: from_attributes = True` on `UserOut` since it gets built from a SQLAlchemy object's attributes, not a plain dict.

Architecture-wise: routes call services, services call repositories, no business logic sits directly in a route. Understood it in theory before, about to actually apply it — next session is the repository layer for `User` (get by email, create user), then the service layer (where the password hashing and "is this email taken" logic actually lives), then the real `/register` endpoint.

Came back to it later today and actually built the repository and service layers. Repository (`repositories/user.py`) ended up being two small functions — `get_user_by_email` and `create_user` — and the point that finally clicked was *why* they have to stay dumb. First pass I wrote in my head had `create_user` also checking for duplicate emails, and it took an example to see why that's wrong: if the duplicate-check logic lives inside the repository, then anything else that ever needs to insert a user (an admin bulk-import script, a test seeding fixtures) is stuck with that rule whether it wants it or not. Repository = mechanism, service = policy, one place to change a rule instead of hunting across three files.

Wrote `create_user` myself (add → commit → refresh → return, matching the pattern from `get_db`), then actually ran both functions against real Postgres — created a test user, confirmed the id and created_at came back populated after refresh, looked it up by email and got it back. Not just "the code runs," actually confirmed the row exists.

Then the service layer — `register_user` in `services/user.py`. This is genuinely the part where things came together: check if the email exists via the repository, raise if it does, hash the password, call `create_user` with the hash instead of the raw password, return the user. Went with a plain `ValueError` instead of raising `HTTPException` directly from the service, so the service layer doesn't need to know FastAPI exists at all — that gets translated to a real HTTP error one layer up, in the route (next session). Tested this one properly too: registered a user and checked the stored password isn't the plaintext I sent in, then tried registering the same email twice and confirmed it actually raises instead of silently creating a duplicate.


End of day: `database.py` → `models/user.py` → `utils/security.py` → `schemas/user.py` → `repositories/user.py` → `services/user.py` are all done and tested against real Postgres. Just the actual `/register` route left before registration works end to end through an HTTP request.

## 2026-08-08

Finished registration end to end today. Wrote `api/auth.py` with an `APIRouter` and the actual `/register` route — this was the first time seeing how the pieces from last session actually connect to an HTTP request: `UserCreate` as a plain parameter gets parsed straight from the request body, `Depends(get_db)` hands the route a DB session and closes it after, and `response_model=UserOut` on the decorator means even though I return the raw SQLAlchemy `User` object, FastAPI filters it through `UserOut` before it ever gets serialized — so the hash literally cannot leak, structurally, not just by convention. Wired it into `main.py` with `app.include_router(auth_router, prefix="/auth", tags=["auth"])` and actually ran the server, hit `/auth/register` with curl against real Postgres — success case, duplicate email (checked it correctly turns the service's `ValueError` into a 400), and a garbage email (learned this one never even reaches my code — Pydantic's `EmailStr` rejects it and FastAPI returns a 422 automatically).

Then moved on to login, which was the first genuinely new concept in a while: JWTs. The idea finally clicked after thinking about *why* you need a signed token at all — HTTP doesn't remember anything between requests, so the server needs some way to trust "this request really is from the user who logged in" without hitting the DB every single time or keeping server-side session state. A JWT is a payload (who you are, when it expires) signed with a secret key the server holds — the client just carries it around and resends it, and the server can verify the signature is legit without looking anything up. Wrote `create_access_token()` in `utils/security.py` using `python-jose`, encoding `sub` (the email) and `exp` (30 min out) and signing with `HS256` and the app's `SECRET_KEY`.

Built `authenticate_user()` in the service layer next and actually caught my own bug before it shipped: first draft used `return ValueError(...)` instead of `raise ValueError(...)` for the failure cases. Looks like a typo but it's a real logic bug — `return`ing an exception just hands back an exception *object* as an ordinary value, it doesn't stop the function or get caught by anything, so the caller would've tried to treat a `ValueError` as if it were a `User` and blown up somewhere completely unrelated later on. Good reminder to actually read what a line does rather than pattern-matching it against `raise` from memory.

Also learned why a failed login should return the exact same error message ("Invalid email or password") whether the email doesn't exist or the password's wrong — if those two cases said different things, anyone could probe the endpoint to find out which emails are registered. Small detail, real security implication.

Wired up `/login` in `api/auth.py`, using `401` instead of `400` for bad credentials (400 is "your request was malformed," 401 is "you're not authenticated" — different thing). Tested all three paths against real Postgres and a running server: correct login (got back a real signed token, decoded it manually with `jose` to confirm `sub`/`exp` were right), wrong password, and an email that doesn't exist — both failure cases correctly returned 401 with the identical generic message.

End of day: registration and login both work end-to-end through real HTTP requests against real Postgres, tokens verified by manually decoding them. Next session: `/users/me`, a protected route that reads the JWT off the `Authorization` header and returns whoever it belongs to — first time building an auth *dependency* rather than just issuing tokens.
