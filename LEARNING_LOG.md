# What I Learned Today

A running log of what I build and learn while working on FreelanceOS, a full-stack SaaS platform for freelancers (React/TypeScript + FastAPI/PostgreSQL, with AI features planned). Building this project end-to-end, hand-in-hand, as part of prep for AI/full-stack engineering roles.

---

## 2026-08-02 — Phase 1: Database layer, first model, Alembic, password hashing, schemas

**Database connection layer (`backend/database.py`)**
- Learned how a SQLAlchemy `engine` (connection pool, built once from a DB URL) differs from a `Session` (one "conversation" with the DB, created per request via `sessionmaker`).
- Learned the `Base` class every ORM model inherits from, and why it exists (lets SQLAlchemy map Python classes to tables).
- Learned the `get_db()` generator + `try/finally yield` pattern FastAPI uses for dependency-injected DB sessions — code before `yield` runs before the route, code after runs after, guaranteeing cleanup.
- Debugged a real `ImportError`/`TypeError` chain from a typo (`Declarative_base` instead of `declarative_base`) and a misuse (subclassing a function instead of calling it) — reinforced that Python is case-sensitive and that `declarative_base` is a *function* to call, not a class to subclass.

**First model (`backend/models/user.py`)**
- Built the `User` SQLAlchemy model: `id`, `email` (unique + indexed), `hashed_password` (never plaintext), `is_active`, `created_at` (timezone-aware, DB-side default via `func.now()`), later added `full_name`.
- Verified the model against a *real* Postgres database, not just "the file parses" — ran `Base.metadata.create_all()` and checked the actual table with `\d users` in psql.
- Hit a real credentials bug: `docker-compose.yml` created Postgres user `freelancer`, but `.env`'s `DATABASE_URL` said `freelanceos` — one-letter mismatch caused `password authentication failed`. Good reminder to read Postgres error messages carefully; "password authentication failed" can actually mean "wrong username."

**Alembic migrations**
- Learned why `Base.metadata.create_all()` isn't a real migration tool — it only creates missing tables, it never alters existing ones. Added `full_name` to the model but the live table didn't get it until a migration was written.
- Set up Alembic (`alembic init`), wired `env.py` to load `DATABASE_URL` from `.env` and to import both `Base` *and* the `User` model (a model has to be imported somewhere for `Base.metadata` to know it exists — this bit me at first).
- Generated a real autogenerated migration (`add full_name to users`), read through the generated `upgrade()`/`downgrade()` functions, learned the gotcha that `nullable=False` with no default fails on non-empty tables, then ran `alembic upgrade head` and confirmed the column landed via psql.

**Password hashing (`backend/utils/security.py`)**
- Learned why passwords are never stored as-is: one-way hashing (bcrypt) means the hash can be verified but not reversed, and bcrypt auto-salts so identical passwords produce different hashes.
- Wrote `hash_password()` / `verify_password()` wrapping a `passlib` `CryptContext` — wrapping the library calls in my own functions so the rest of the app doesn't care which hashing library is underneath.
- Debugged a real dependency conflict: `passlib==1.7.4` doesn't understand `bcrypt==5.0.0`'s API (`bcrypt.__about__` was removed), causing a cryptic `password cannot be longer than 72 bytes` error that had nothing to do with my code. Fixed by pinning `bcrypt==4.0.1` explicitly in `requirements.txt`. Lesson: unpinned transitive dependencies can silently break things that "aren't my code."

**Pydantic schemas (`backend/schemas/user.py`)**
- Learned why API schemas are separate from DB models: `UserCreate` (accepts plaintext `password` from the client), `UserOut` (safe response shape — no password field, ever), `UserLogin`.
- Learned `class Config: from_attributes = True` — lets a schema be built from an object's *attributes* (like a SQLAlchemy row) instead of only from a dict. Without it, `UserOut.model_validate(some_user)` would fail.
- Proved to myself that `UserOut` really can't leak `hashed_password` even when given a full user-like object with that field present — it only reads the fields explicitly declared on the schema.
- Hit another `NameError` from forgetting to import `datetime` before using it as a type hint — same category of bug as the database.py typo, good pattern to recognize going forward.

**Architecture note learned:** routes → services → repositories. Business logic never lives directly in a route function; routes just parse/validate input and call a service, services hold the actual logic, repositories do the raw DB queries. About to apply this for the first time on the register endpoint.
