2026-08-02

SQLAlchemy core pieces:
- engine: connection pool to the DB, built once from a DB URL via create_engine(url). Lazy - doesn't
  actually connect until something uses it.
- Session: one "conversation" with the DB (tracks loaded/changed objects, commits/rolls back as a unit).
  Don't create directly - use a factory.
- sessionmaker(bind=engine): factory that produces Session objects. autocommit=False, autoflush=False
  is the standard default (don't write to DB until .commit() is called explicitly).
- Base (declarative_base() or class Base(DeclarativeBase)): base class every ORM model inherits from,
  so SQLAlchemy knows to map the class to a table.
- get_db() pattern for FastAPI:
    def get_db():
        db = SessionLocal()
        try:
            yield db
        finally:
            db.close()
  FastAPI runs the code before yield, hands the route the value, then runs the code after yield
  once the route is done - guarantees cleanup even on exceptions.

Model definition (SQLAlchemy 2.0 style):
    class User(Base):
        __tablename__ = "users"
        id: Mapped[int] = mapped_column(primary_key=True)
        email: Mapped[str] = mapped_column(String, unique=True, index=True)
    Mapped[...] + mapped_column(...) is the modern typed style. unique=True enforces no duplicates
    at the DB level. index=True speeds up lookups (important for anything queried often, like email
    on login).

create_all() vs migrations:
    Base.metadata.create_all(bind=engine) only creates tables that don't exist yet. It will NOT alter
    an existing table if the model changes (e.g. adding a column). That's what Alembic is for.

Alembic:
    alembic init alembic          -> scaffolds alembic.ini + alembic/env.py + alembic/versions/
    env.py needs:
      - target_metadata = Base.metadata  (so it knows what tables *should* exist)
      - the actual model files imported (e.g. `from models.user import User`) - metadata is empty
        until a model class has actually executed once
      - the DB URL, either from alembic.ini or overridden at runtime via
        config.set_main_option("sqlalchemy.url", ...)
    alembic revision --autogenerate -m "message"   -> diffs models against live DB, writes a migration
    alembic upgrade head                            -> applies pending migrations
    Migration file has upgrade() and downgrade() - downgrade is the reverse operation, for rollback.
    Gotcha: adding a NOT NULL column with no default fails if the table already has rows (nothing to
    fill existing rows with). Need nullable=True, a server_default, or a backfill step.

Password hashing:
    Never store plaintext passwords. Hash with bcrypt (one-way - can verify, can't reverse). bcrypt
    auto-salts, so the same password hashed twice gives different output (defeats rainbow tables).
    passlib.context.CryptContext(schemes=["bcrypt"], deprecated="auto") wraps this.
    .hash(password) -> hash string to store
    .verify(password, hashed) -> True/False
    Bug hit: passlib 1.7.4 + bcrypt 5.0.0 don't get along (passlib's version-detection code references
    an attribute bcrypt 5.x removed). Symptom was a totally unrelated-looking error about 72-byte
    password limits. Fix: pin bcrypt==4.0.1 in requirements.txt. Lesson - weird errors can come from
    dependency version mismatches, not just your own code.

Pydantic schemas (v2):
    Separate from SQLAlchemy models on purpose. Models = DB shape. Schemas = API input/output shape.
    UserCreate: what registration accepts (plaintext password field, not hashed_password)
    UserOut: what gets sent back - deliberately excludes hashed_password. Since Pydantic only reads
      fields you explicitly declared on the schema, it can't leak fields that aren't declared, even
      if you pass in an object that has them.
    UserLogin: email + password for login.
    class Config: from_attributes = True (Pydantic v2) - needed when building a schema from an object's
      *attributes* (like a SQLAlchemy row: user.id, user.email) instead of a dict. Without it,
      UserOut.model_validate(some_orm_object) fails. Old v1 name was orm_mode - don't use that in v2,
      it's silently ignored.

Architecture pattern (used throughout the project):
    routes -> services -> repositories
    - routes: parse/validate the HTTP request, call a service, return a response. No logic.
    - services: the actual business logic (e.g. "hash the password", "check email isn't taken").
    - repositories: raw DB queries only, no logic. Reusable, dumb, testable in isolation.

Repository layer (repositories/user.py):
    get_user_by_email(db, email) -> User | None
        db.query(User).filter(User.email == email).first()
        .filter() with a model column uses == overloaded to build SQL WHERE, not a python compare.
        .first() -> match or None.
    create_user(db, email, hashed_password, full_name) -> User
        user = User(...)
        db.add(user)      # stage in session, not written yet
        db.commit()        # write to Postgres
        db.refresh(user)   # reload from DB so id/created_at (DB-generated) are populated on the object
        return user
    Why repositories stay "dumb" (no business rules inside them):
        if create_user also checked for duplicate emails, every other caller (bulk import script,
        test fixtures, etc.) would be forced into that rule too, and the actual rule would be
        scattered across files instead of living in one place (the service).

Service layer (services/user.py):
    register_user(db, user_create: UserCreate) -> User
        1. existing = get_user_by_email(db, user_create.email)
        2. if existing: raise ValueError("Email already registered")
        3. hashed = hash_password(user_create.password)
        4. return create_user(db, user_create.email, hashed, user_create.full_name)
    Raised a plain ValueError instead of FastAPI's HTTPException directly - keeps the service layer
    framework-agnostic (doesn't need to import fastapi at all). The route layer will catch this and
    translate it into a real HTTP error response.

Type hints (e.g. `-> User` on a function signature):
    Python does NOT enforce these at runtime - a function typed `-> User` could still `return None`
    and nothing would stop it at the moment it runs. They're for tooling:
    - editor autocomplete/hover knows what fields exist on the return value
    - a type checker (mypy, editor's built-in one) can flag a wrong return type before running anything,
      instead of surfacing as a confusing AttributeError later when something calls .field on the
      wrong type
    Basically free correctness-checking, no runtime cost, worth using consistently.

Testing repo/service functions directly (without a route yet):
    Can call them straight from a python -c script using a real SessionLocal():
        from database import SessionLocal
        db = SessionLocal()
        ... call functions, print results, db.close()
    Useful for proving something works end-to-end against real Postgres before the HTTP layer exists.

FastAPI routing (api/auth.py):
    APIRouter() - a mini sub-app. Defined separately from the main `app`, then mounted onto it.
    app.include_router(router, prefix="/auth", tags=["auth"]) in main.py:
        - prefix: every route in this router gets prepended, e.g. /register -> /auth/register
        - tags: groups routes together in the auto-generated /docs UI
    A Pydantic model used as a plain parameter (not Depends(...)) is read from the request body and
    auto-validated, e.g. `def register(user_create: UserCreate, ...)`.
    Depends(get_db) - FastAPI calls get_db(), runs the route with the yielded session, then resumes
    get_db() after the route returns to close it (works even if the route raises).
    response_model=UserOut on the decorator - filters whatever the route returns through UserOut
    before serializing, even if the actual returned object (e.g. a raw User row) has extra fields
    like hashed_password. Structural guarantee, not just convention.
    ValueError -> HTTPException translation happens in the route, not the service:
        try: ... except ValueError as e: raise HTTPException(status_code=400, detail=str(e))
    Status code choice matters: 400 = bad/malformed request (e.g. duplicate email on register),
    401 = not authenticated (e.g. wrong password on login). Different semantic meaning.
    Pydantic validation (e.g. EmailStr rejecting a bad email) happens before the route function even
    runs - returns 422 Unprocessable Entity automatically, not something to catch manually.

JWTs (JSON Web Tokens):
    Why: HTTP is stateless - server doesn't remember previous requests. A JWT is a signed blob the
    client stores and resends (Authorization: Bearer <token>), letting the server verify "this is a
    legit request from an authenticated user" via signature check alone - no DB lookup or server-side
    session storage needed.
    Structure: header.payload.signature (all base64). Payload is just claims (data), NOT encrypted -
    anyone can decode and read it, they just can't forge or modify it without invalidating the
    signature (since they don't have SECRET_KEY). Don't put secrets in the payload.
    python-jose library:
        jwt.encode(payload_dict, SECRET_KEY, algorithm="HS256") -> token string
        jwt.decode(token, SECRET_KEY, algorithms=["HS256"]) -> payload dict (raises if signature
            invalid or "exp" has passed)
    Standard claims used: "sub" (subject - who the token is about, e.g. user's email), "exp"
    (expiration - unix timestamp; jose enforces this automatically on decode).
    create_access_token(data: dict) pattern:
        to_encode = data.copy()              # don't mutate caller's dict
        to_encode.update({"exp": expire})     # expire = now (UTC) + timedelta(minutes=30)
        return jwt.encode(to_encode, SECRET_KEY, algorithm="HS256")
    HS256 = HMAC-SHA256, symmetric signing (same SECRET_KEY signs and verifies). Fine for a single
    backend service; asymmetric (RS256) matters more with multiple services verifying tokens without
    all holding the signing key.
    Token response shape (OAuth2 convention): {"access_token": "<jwt>", "token_type": "bearer"} -
    token_type tells the client how to send it back (Authorization: Bearer <token>).

authenticate_user() pattern (services/user.py):
    1. user = get_user_by_email(db, email); if not user: raise ValueError(...)
    2. if not verify_password(plain, user.hashed_password): raise ValueError(...)
    3. return user
    Both failure cases raise the SAME error message ("Invalid email or password"). Deliberate -
    if "no such user" and "wrong password" had different messages, an attacker could enumerate
    which emails are registered just by trying logins. Same principle as generic login failure
    messages on any real auth system.
    Bug caught during this session: wrote `return ValueError(...)` instead of `raise ValueError(...)`
    on the first pass. `return`ing an exception just hands it back as a normal value - doesn't stop
    execution, doesn't get caught by `except ValueError`. Caller would've received a ValueError
    object where it expected a User, and blown up somewhere unrelated later (e.g. calling .email on
    it). Looks like a typo but is a real control-flow bug - worth double-checking raise vs return
    whenever writing error paths.

Manually decoding a JWT to verify it (useful for testing before a protected route exists to do it):
    from jose import jwt
    jwt.decode(token, SECRET_KEY, algorithms=["HS256"])  # -> {"sub": ..., "exp": ...}
    Confirms signature is valid and expiry is set correctly, without needing a route that consumes it.
